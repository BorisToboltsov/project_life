## Граница фронтенда и бэкенда

Единственный канал — HTTP JSON API под префиксом `/api`. Контракт описывает OpenAPI,
который отдаёт сам бэкенд (`/api/openapi.json`, Swagger UI — `/api/docs`). Из него
генерируются типы фронтенда (`frontend/src/api/schema.d.ts`), запросы идут через
типизированный клиент `openapi-fetch`.

Фронтенд и API живут на одном origin: Caddy отдаёт статику и проксирует `/api/*`. CORS не
нужен.

## Внешние сервисы

Один — [Open Food Facts](https://world.openfoodfacts.org): бэкенд спрашивает у него продукт
по штрихкоду, которого нет в своём каталоге, и ищет продукты по названию. Наружу уходит
только штрихкод или текст поиска (I11); браузер за пределы своего адреса не ходит.

| Настройка | Что задаёт |
|-----------|------------|
| `LIFE_OFF_URL` | адрес запроса по штрихкоду; пустое значение выключает все обращения наружу |
| `LIFE_OFF_SEARCH_URL` | адрес поиска по названию; пустое значение выключает только его |
| `LIFE_OFF_PRODUCTS_PER_MINUTE`, `LIFE_OFF_SEARCHES_PER_MINUTE` | сколько обращений в минуту сервер себе позволяет; по умолчанию — ниже пределов сервиса, поднимает их только стенд |

Решения — в [ADR 0009](adr/0009-barcode-scanner.md) и
[ADR 0010](adr/0010-name-search-and-label.md).

## Контейнеры

Описаны в `deploy/compose.yaml` — этот файл как есть лежит на сервере и берёт образы из
реестра. Стенд для e2e добавляет к нему `deploy/compose.build.yaml`, который собирает
образы из исходников.

| Сервис | Образ | Роль |
|--------|-------|------|
| `db` | `postgres:18` | данные; том `db` |
| `migrate` | образ бэкенда | разово выполняет `alembic upgrade head` и завершается |
| `backend` | `backend/Dockerfile` | API на uvicorn; стартует после успешных миграций; порт наружу не публикуется |
| `web` | `frontend/Dockerfile` | Caddy со сборкой фронтенда; единственный сервис с открытыми портами |

Адрес сайта задаёт переменная `SITE_ADDRESS`: домен на сервере (сертификат Caddy получает
сам) или `:80` на стенде для e2e.

## Выкладка

Решение и его причины — в [ADR 0005](adr/0005-deployment.md), шаги — в
[INSTALL.md](INSTALL.md).

- CI после всех гейтов публикует образы `project_life-backend` и `project_life-web` в
  GitHub Container Registry: тег `latest` и тег `<версия>-<коммит>`.
- На сервере администратор запускает `life-update`: тот скачивает `latest` и, если образы
  изменились, делает бэкап и перезапускает контейнеры. Само приложение не обновляется;
  доступа к серверу у GitHub нет.
- `life-backup` (таймер, ежедневно, и перед каждым обновлением) пишет дамп базы,
  зашифрованный открытым ключом age, в `/opt/life/backups/`.
- `deploy/install.sh` раскладывает `compose.yaml`, скрипты и таймер бэкапа в `/opt/life` и
  создаёт `.env` с секретами. Наружу открыты только TCP 80 и 443.

## Бэкенд

- `app.main` — фабрика приложения. Роутеры собраны в три группы: открытая, для вошедших
  и для администратора; защита вешается на группу целиком.
- `app.config` — настройки из окружения с префиксом `LIFE_`.
- `app.db` — движок, фабрика сессий, базовый класс моделей с соглашением об именах
  ограничений.
- `app.log` — логи одной JSON-строкой на запись, включая логи uvicorn.
- `app.errors` — коды ошибок API (`ErrorCode`) и исключение `ApiError`.
- `app.schemas` — схемы запросов и ответов вместе с ограничениями значений.
- `app.models` — модели SQLAlchemy.
- `app.metrics` — справочник штатных показателей (четыре начальных и семь рекомендуемых):
  величина, каноническая единица, допустимый диапазон; общий диапазон своего показателя;
  здесь же пересчёт единиц.
- `app.exercises` — справочник штатных упражнений: что записывает подход, какие мышцы
  работают и помогают, какие поля есть у кардио и в чём у него показывать темп.
- `app.fitness` — справочник физических тестов: коды тестов, варианты отжиманий, пределы
  дистанции Купера и повторов, пересчёт миль в метры.
- `app.api.workouts` — время тренировки, её упражнения и подходы; проверка вида подхода,
  предыдущий результат и повтор тренировки. Прогресс считается в `app.api.exercises`.
- `app.nutrition` — предустановленные приёмы пищи, единицы продукта, источники продукта,
  меры количества (порция и упаковка), энергия белков, жиров и углеводов, пересчёт порций
  в единицы продукта и состава на 100 единиц — в съеденное.
- `app.barcodes` — штрихкод продукта: проверка контрольной цифры и единый вид записи.
- `app.security` — хэши паролей (argon2id), JWT, случайные токены и их хэши.
- `app.services` — логика без HTTP: сессии с ротацией refresh-токена, ограничение частоты
  входа, одноразовые ссылки, состав и сохранение отчётов об ошибках, клиент Open Food
  Facts (`open_food_facts`) и ограничение частоты в памяти процесса (`rate_limit`).
- `app.api` — роутеры и зависимости `current_user` / `require_admin`; клиент Open Food
  Facts эндпоинт получает зависимостью `OpenFoodFactsDep`.
- `app.cli` — команды администратора сервера (`python -m app.cli invite --admin`).

### Показатели

Все числовые показатели лежат в одной таблице `measurements` и различаются видом замера —
записью из списка пользователя в таблице `metrics` ([ADR 0012](adr/0012-own-metrics.md)).
Штатный вид хранит код из справочника `app.metrics`, свой — название и величину. Каждый
начинает с четырёх штатных; остальные штатные добавляются по коду, свои — с ключом от
клиента. Вид убирают из списка, а не удаляют: замеры остаются (инвариант I13), сводка
отдаёт последний замер и по убранным видам.

Клиент присылает значение и единицу, как их ввёл пользователь; сервер проверяет, что
единица той же величины, что у вида, а значение — в его диапазоне, пересчитывает в
каноническую единицу и хранит оба значения ([ADR 0004](adr/0004-units.md)). Ключ записи
выбирает клиент ([ADR 0002](adr/0002-record-ids.md)), местную дату — тоже
([ADR 0003](adr/0003-time.md)).

`GET /api/measurements/all` отдаёт все замеры пользователя для копии без сети, новыми
первыми, с меткой `ETag`: неизменные — ответ 304 без тела ([ADR 0020](adr/0020-offline-entry.md)).

### Упражнения

Решения — в [ADR 0014](adr/0014-exercises.md). Упражнение — запись в списке пользователя
в таблице `exercises`, как вид замера. Штатное хранит код из справочника `app.exercises`,
своё — название и мышцы; вид подхода есть у обоих и после создания не меняется. Список
начинается пустым: штатное добавляется по коду, своё — с ключом от клиента. Упражнение
убирают из списка, а не удаляют (инвариант I14).

`GET /api/exercises` отдаёт список пользователя вместе с убранными и справочник целиком:
вид подхода, основные и помогающие мышцы, поля кардио. Название, шаги техники и рисунок
штатного упражнения живут на фронтенде и обязаны быть у каждого (инвариант I15).
### Журнал тренировок

Решение — в [ADR 0016](adr/0016-workout-journal.md). `GET /api/workouts` возвращает историю;
`GET`, `PUT` и `DELETE /api/workouts/{id}` читают, создают, правят время и удаляют тренировку.
`POST /api/workouts/{id}/finish` завершает её, `/repeat` создаёт повтор с пустыми подходами.
Повтор и запуск группы принимают необязательный `exercise_ids` — упражнения строк, каким их
видел клиент; если состав с тех пор изменился, ответ — 409 `workout_source_changed` (I17).
`GET /api/workouts/recent` отдаёт копию журнала для работы без сети: тренировки последних
14 дней по часовому поясу профиля и незавершённую — целиком, и последние подходы по
каждому упражнению ([ADR 0020](adr/0020-offline-entry.md)).
Вложенные `PUT` и `DELETE /api/workouts/{id}/exercises/{item_id}` управляют составом,
а `…/sets/{set_id}` — подходами. Все эти маршруты требуют входа и проверяют владельца.
`PUT /api/exercises/{id}/rest` сохраняет отдых; `GET /api/exercises/{id}/progress`
вычисляет график и рекорды по завершённым тренировкам. У кардио ответ несёт ещё единицу
темпа из справочника, лучший темп по подходам от 1 км и по точке на тренировку — самую
длинную дистанцию, самое долгое время и лучший темп ([ADR 0021](adr/0021-fitness-tests.md)).

### Физические тесты

Решения — в [ADR 0021](adr/0021-fitness-tests.md). Результат теста — отдельная запись
`fitness_results`, не подход тренировки. `GET /api/fitness-results` отдаёт все результаты
пользователя, новыми первыми, с меткой `ETag`: неизменные — ответ 304; тот же ответ лежит
в копии без сети. `PUT` и `DELETE /api/fitness-results/{id}` вносят, правят и удаляют
результат. Запись хранит только то, что человек сделал; тест и вариант отжиманий не
меняются (инвариант I21). VO2max и оценку по нормам считает фронтенд
(`frontend/src/lib/fitness.ts`).

### Группы тренировок

`app.api.workout_groups` обслуживает `GET /api/workout-groups` (с необязательным днём
`day`), `PUT` и `DELETE /api/workout-groups/{id}` и `POST /api/workout-groups/{id}/start`.
Таблица `workout_groups` хранит название, недельное расписание, отдельные даты и архив;
`workout_group_exercises` — состав и порядок. `workouts.source_group_id` связывает
созданную тренировку с источником для повторяемого запуска. План на сегодня вычисляется
в часовом поясе профиля. Решение — в [ADR 0017](adr/0017-workout-groups.md).

### Питание

`GET /api/products/catalog` отдаёт каталог целиком для копии без сети, с меткой `ETag`:
неизменный каталог — ответ 304 без тела; в метку входит и тот, кто спрашивает, — от него
зависит `editable`. `GET /api/diary/recent` — 14 последних дней дневника по часовому
поясу профиля, каждый такой же, как отдельный `GET /api/diary` ([ADR 0020](adr/0020-offline-entry.md)).

`GET /api/diary/stats?period=week|month&date=YYYY-MM-DD` возвращает календарный период,
дневные суммы и цели, средние и крайние замеры веса. `app.services.diary_statistics`
собирает результат четырьмя запросами к существующим таблицам. Фронтенд —
`pages/diary/StatisticsPage.tsx`, маршрут `/diary/stats`, ленивый `CaloriesChart`.
Кэш статистики входит в `DIARY_KEY` и сбрасывается также при изменении замеров.
Решение — [ADR 0019](adr/0019-nutrition-statistics.md).

Решения — в [ADR 0007](adr/0007-food-diary.md) и [ADR 0008](adr/0008-meals-units-goal.md).
Каталог продуктов общий: читает любой вошедший, меняет автор или администратор. Продукт
измеряется в граммах или миллилитрах, состав задан на 100 таких единиц. Запись дневника —
количество продукта в приёме пищи за день; при создании в неё снимается название, единица
и состав продукта, и дальше она от каталога не зависит (I10). Сахара, насыщенные жиры,
клетчатка и соль у продукта необязательны; в запись они снимаются, а в съеденное и в цели
не входят ([ADR 0010](adr/0010-name-search-and-label.md)).

Количество записи приходит одним из двух способов: в единицах продукта (`amount`) или его
порциями и упаковками (`portion` — вид меры и их число); во втором случае единицы считает
сервер по размеру меры. Размер снимается в запись вместе с составом и живёт по тем же
правилам. Подсказки (`GET /api/diary/suggestions`) несут, как продукт внесли в прошлый
раз. Параметр `product_id` этого запроса возвращает историю выбранного продукта без
ограничения списками подсказок. Решения — в [ADR 0013](adr/0013-portions.md).

`GET /api/products?q=…&offset=…` отдаёт каталог страницами по 20 по алфавиту. Ответ —
список продуктов; откуда продолжать, говорит заголовок `X-Next-Offset`, а на последней
странице его нет.

Приёмы пищи — список пользователя в таблице `meals`. Четыре предустановленных создаются
вместе с учётной записью (`preset_meals` в `app.models.nutrition`), свои добавляет
пользователь. `DELETE` убирает приём из списка, но строку оставляет: дни, где в нём есть
записи, показывают его по-прежнему.

`GET /api/diary?date=…` отдаёт день целиком: приёмы пищи из списка и убранные с записями
этого дня, записи, съеденное за приём и за день, воду и цель, действовавшую в этот день.
Съеденное считает сервер, в `app.nutrition`. Цель задаётся по любому набору показателей;
её калории — предел для энергии белков, жиров и углеводов, это проверяет схема запроса.

Вода — порции в таблице `water_intakes`: день и миллилитры, ключ от клиента. Выпитое за
день — их сумма; в ответе дня она идёт вместе с самими порциями в порядке внесения. Цель
по воде — показатель `water_ml` той же цели на день; запрос цели без него оставляет цель
по воде прежней. Решения — в [ADR 0011](adr/0011-water.md).

`POST /api/products/lookup` ищет продукт по штрихкоду: свой каталог → память о ненайденном
(`barcode_misses`, семь дней) → Open Food Facts. Ответ — один из четырёх исходов: `found`
с продуктом, `draft` с тем, что известно, `not_found` или `unavailable`. Полный продукт из
источника сразу сохраняется в каталог с источником `open_food_facts` и автором — тем, кто
сканировал; ключ ему выдаёт сервер, от дублей защищает уникальность штрихкода. Разбор
ответа источника в мерки каталога — `parse` в `app.services.open_food_facts`. Обращения
наружу ограничены на пользователя (отказ 429) и на всё приложение (исход `unavailable`).

`GET /api/products/external?q=…&page=…` ищет продукты по названию в Open Food Facts и
отдаёт страницу тех, которых ещё нет в каталоге: штрихкод, название на языке пользователя
и то, что известно о составе. Ничего не сохраняет: выбранный продукт клиент берёт в
каталог тем же `POST /api/products/lookup`. Текст поиска уходит наружу в виде
`search_terms`, страница ответа помнится в памяти процесса десять минут. Пределы у поиска
свои, исходы те же: 429 и `unavailable`.

Подсказки выводятся из собственных записей пользователя вместе с количеством, которое он
вносил в прошлый раз: «недавние» и «частые» — по всему дневнику, а с `meal_id` в запросе —
ещё и то, что чаще всего вносят в этот приём пищи. Копирование записей на другой день —
один запрос; ключи копий присылает клиент.

### Сбор ошибок

Решение и его причины — в [ADR 0006](adr/0006-error-collection.md). Отчёт попадает в
`error_reports` двумя путями, оба — в `app.api.error_reports`:

- обёртка `CaptureErrors` вокруг приложения записывает необработанное исключение запроса
  и пропускает его дальше — в логи и в ответ 500;
- `POST /api/errors` принимает отчёт от приложения в браузере.

Повтор той же ошибки увеличивает счётчик в существующей строке. Отчёты видны
администратору в разделе «Управление».

### Вход

Схема описана в [ADR 0001](adr/0001-auth-jwt.md). Access-JWT клиент шлёт в заголовке
`Authorization`; refresh-токен лежит в cookie, доступном только `/api/auth`, и меняется
при каждом обновлении.

## Фронтенд

- `src/main.tsx` — точка входа: провайдеры, регистрация service worker, старт сессии,
  подключение сбора ошибок.
- `src/app/` — `App` (экраны загрузки и «нет связи»), дерево маршрутов с защитой
  (`router.tsx`), рамки `AuthLayout` и `AppShell`, отправка отчётов об ошибках
  (`errorReporting.ts`), экран сбоя (`CrashScreen.tsx`) — роутер ставит его на место
  экрана, упавшего при отрисовке; новая версия приложения (`appUpdate.ts`) и строка с
  предложением обновиться (`UpdatePrompt.tsx`).
- `src/auth/` — сессия: access-токен в памяти, обновление одним общим запросом, выход.
  Защищённая рамка `AppShell` передаёт пользователя экранам через `UserContext` и
  размонтирует их при закрытии сессии, не дожидаясь перехода роутера на вход.

  запрос после его обновления.

  проверка связи, отправка очереди

  поиск, когда вернулась связь, и тело записи для найденного продукта (`deferred.ts`);
  владелец копии и её стирание (`session.ts`); состояние для полосы и отметок
  (`store.ts`).
- `src/i18n/` — словари и выбор языка: до входа — язык браузера или сохранённый выбор,
  после входа — язык из профиля.

  UUIDv7, сопоставление ошибок API ключам словаря, разбор стека исключения, калории по

Маршруты делятся на гостевые (`/login`, `/invite`, `/reset`) и приложение (`/`,
`/diary/…`, `/products/…`, `/measurements/…`, `/workouts/…`, `/unsent`, `/more`, `/profile`,
`/admin`). Раздел «Тренировки» открывает журнал; `/workouts/$id` — одну тренировку,
`/workouts/exercises` — список упражнений, `/workouts/tests/$test` — экран теста,
`…/new` и `…/$id` — новый результат и правка. Адрес карточки упражнения несёт код штатного
или ключ своего. Проверка на маршруте — удобство, а данные закрывает бэкенд.

Экраны подключаются в `router.tsx` лениво (I12): первая загрузка несёт рамку приложения,
экран приходит отдельным куском сборки при переходе. Service worker при установке кладёт в
кэш всю сборку, поэтому без сети открывается любой экран.

Новую версию service worker скачивает в фоне и ждёт: `main.tsx` передаёт её в `appUpdate`,
строка `UpdatePrompt` предлагает обновиться, нажатие включает новую версию и перезагружает
страницу. Открытое приложение само спрашивает сервер о новой версии, когда его
разворачивают, но не чаще раза в час.

Кэш запросов (TanStack Query) принадлежит одному пользователю и очищается при смене
вошедшего.

Запись по незнакомому штрихкоду (`/diary/$date/barcode/$id` — исправить найденный или
заполнить ненайденный продукт) живёт в таблице `deferred` базы на устройстве, а не в
очереди: сервер узнаёт о ней только записью дневника, когда человек внёс найденный
продукт, — под тем же ключом.

Журнал тренировок, упражнения, группы, дни дневника, цель и подсказки читаются через
копию на устройстве: ответ сервера сохраняется в IndexedDB, без связи экран берёт его
оттуда. Поиск по каталогу, продукт и его история в копию не кладутся: без связи они
собираются из каталога и дней копии. Изменения журнала, записей дневника и воды уходят
через очередь: при обрыве связи они встают в неё и сразу вносятся в копию (I20). Рамка
приложения передаёт копию вошедшему (`useOfflineSync`) и, когда связь вернулась и
очередь опустела, перечитывает данные экранов с сервера. Без связи при запуске сессия
открывается на сохранённом пользователе без токена; токен обновится с первым запросом.

### Рецепты

`Product.recipe` — JSONB со снимками ингредиентов и выходом блюда. `services/recipes.py`
вычисляет состав и проверяет граф вложений. `PUT /api/products/{product_id}` принимает
продукт либо рецепт; поиск принимает `kind=all|products|dishes`. Форма — `DishForm.tsx`.
