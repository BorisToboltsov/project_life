# ADR 0023. Файлы и исследования внутри «Здоровья»

Статус: архитектурный подход принят, 2026-10-19; этапы 0.13.0 (2026-10-20)
и 0.13.1 (2026-10-23) реализованы; просмотр 0.13.2 реализован, аппаратная проверка впереди.
Согласованы свой сервер, загрузка только с сетью, целые исследования КТ/МРТ,
навигация внутри карточки «Здоровье», Garage, отдельный обработчик импорта
и встроенный просмотр Cornerstone3D. Актуальная реализация просмотра описана в конце
решения; работа на физических iOS/Android остаётся условием закрытия 0.13.
Если аппаратная проверка не пройдёт, путь отрисовки пересматривается до выпуска.

## Контекст

В 0.12 есть бланки анализов с числовыми результатами. Вложения отсутствуют;
резервная копия содержит только PostgreSQL. Теперь нужны оригиналы бланков и архивы
КТ/МРТ с сериями, кадрами и заключением. Браузер обращается только к домену приложения
(I11), данные разных пользователей изолированы (I5), экраны загружаются лениво (I12).

## Решение

### Пользовательская модель

Карточка «Здоровье» содержит входы «Анализы» и «Исследования». Снимки открываются по пути
«Здоровье → Исследования → исследование → просмотр»; файлы анализов — внутри бланка.
Остальное содержимое и расположение карточки сохраняются. Общая лента не требуется.

Исследование — самостоятельная запись внутри здоровья: название, дата, учреждение,
заметка, заключение PDF/фото и DICOM. Оно не требует создания бланка анализов.
Два типа записей используют общее хранилище вложений. Файл принадлежит ровно одному
бланку или исследованию. В 0.13.0 внешний ключ связывает вложение с бланком,
а API проверяет совпадение владельца обеих записей при каждой операции. В 0.13.1
принадлежность вложений бланкам и исследованиям закреплена составными внешними
ключами и ограничением единственного родителя на уровне БД.

PDF, JPEG и PNG прикрепляются к уже синхронизированному родителю. ZIP исследования
проверяется на сервере, после чего человек видит найденные исследования, серии,
имя пациента и предупреждения и подтверждает импорт. Имя пациента — только для проверки:
владельца определяет авторизованная сессия. Архив с несколькими исследованиями предлагает
выбор; импорт создаёт отдельную запись для каждого выбранного исследования. Клиент
назначает UUIDv7 каждой записи; подтверждение выбора с теми же ключами идемпотентно.
Загруженный архив хранится один раз у владельца; ссылки выбранных исследований на него
учитываются при очистке, удаление одной записи не удаляет оригинал другой.

### Garage и неизменяемые оригиналы

Выбран Garage в Compose, один узел с постоянным томом, доступный только через
Caddy/внутреннюю сеть. Один узел не даёт отказоустойчивости; копия вне сервера обязательна
для защиты от потери диска. Собственный каталог файлов с самописной загрузкой не выбран:
S3 даёт стандартные multipart и подписи. Другие S3-серверы можно подключить через адаптер.
Отсутствие versioning в Garage компенсируется неизменяемыми ключами и резервными копиями.

Временный bucket для загрузки отделён от опубликованных оригиналов. Браузер получает
подписанный UploadPart на конкретный объект/часть на 15 минут; подпись включает
Content-Length ожидаемой части. Caddy
проксирует bucket-prefix без изменения подписанных пути и Host; домен тот же.
API резервирует квоту, ограничивает число/размер частей и параллельных сессий;
Caddy ограничивает тело запроса частью (предлагается 8 МиБ). Фактический размер и hash
проверяет сервер, полям клиента доверять нельзя. Подпись сама по себе не заменяет квоту.

После завершения multipart доступ на запись к загрузке закрыт. Для одиночного PUT
сервер фиксирует ожидаемый ETag и выполняет условное копирование; несовпадение требует
повторной проверки. Затем проверяется именно приватная копия: размер, SHA-256, MIME,
разбор содержимого. Только после этого транзакция публикует ссылку на неё. Старый
подписанный PUT не может изменить проверенный/опубликованный объект. Временные ключи
не переиспользуются; запоздалые загрузки убираются после срока жизни всех подписей.

Получение файлов и кадров — авторизованный потоковый API с Range, `nosniff`, безопасным
Content-Disposition и `Cache-Control: private, no-store`. Права проверяются на каждом
запросе. PDF открывается через контролируемый просмотр, активное содержимое не получает
доступ к приложению. Внешних CDN, публичных bucket и URL для совместного доступа нет.
Подписи, оригинальные имена и DICOM-поля не попадают в логи/отчёты ошибок.

### Загрузка, обработка и удаление

В БД: UUIDv7 вложения, владелец, родитель, оригинальное имя, MIME, размер, hash,
непрозрачный object key; отдельно upload session и импорт. Статусы файла:
`uploading → verifying → ready`, ошибки `failed`, отмена/удаление отдельными состояниями.
Импорт: `inspecting → awaiting_confirmation → importing → ready/failed`.

Ссылки частей обновляются через API; после обрыва можно повторить только недостающие части.
После перезапуска браузера нужно снова выбрать файл и сверить уже принятые части.
Бинарные файлы не сохраняются в IndexedDB/Service Worker. Без сети доступны сохранённые
метаданные с пояснением; просмотр и добавление файлов требуют сети. Офлайн-запись
числовых анализов остаётся прежней.

Обработка выполняется отдельным ограниченным worker, без исходящего интернета.
Рекомендуется Procrastinate на существующем PostgreSQL вместо собственной очереди:
повторы, блокировки задач, heartbeat и восстановление зависших работ. Его основу из
0.15 потребуется ввести уже в 0.13; уведомления остаются в 0.15. Совместимость с
Python 3.14 и сценарии падения worker проверить до фиксации версии зависимости.
Задачи идемпотентны, публикация результата повторно проверяет владельца, родителя и отмену.

ZIP распаковывается потоково с лимитами фактических байтов, файлов, памяти и времени.
Запрещены выход из каталога, symlink, шифрованные/вложенные архивы. Программы просмотрщиков
с диска не запускаются. Пропущенные/повреждённые файлы показываются до подтверждения;
частичный импорт не маскируется под полный. Оригинальный архив сохраняется.

Стартовое предложение лимитов: вложение 50 МиБ, ZIP 2 ГиБ, распаковка 8 ГиБ,
20 000 файлов и квота 20 ГиБ на пользователя. Резервируется пиковое место с учётом
архива, распаковки и производных объектов; проверяется общий свободный диск. Лимиты
настраиваемые, окончательные значения зависят от сервера. Лимит кадров и пикселей
проверяется отдельно: один multiframe-файл не обходит ограничения количеством файлов.

Удаление сразу закрывает доступ, отменяет задания; физическая очистка повторяется
в фоне. Офлайн-удаление бланка при синхронизации каскадно удаляет его вложения.
Удаление исходного архива с несколькими исследованиями учитывает оставшиеся ссылки.

### DICOM: индекс и просмотр

Индекс в PostgreSQL: исследования → серии → экземпляры → кадры. UID из DICOM не
является ключом авторизации. Совпадающие UID разных владельцев не объединяются.
В пределах исследования одинаковый UID/hash — повтор, разное содержимое — конфликт.
Порядок срезов определяется пространственными координатами/ориентацией; разные
геометрии и временные фазы разделяются. Для Enhanced CT/MR читаются per-frame metadata.
Если геометрии недостаточно, fallback-порядок сопровождается явной отметкой.

Выбран Cornerstone3D Stack Viewport, локально поставляемые кодеки и worker,
ленивая загрузка на экране просмотра. Один viewport, серии, срезы, масштаб, перемещение,
окно/уровень, ориентационные метки при корректной геометрии. MPR/3D, измерения,
сегментация, подключение PACS/DIMSE и автоматические медицинские выводы в объём не входят.

Большой multiframe нельзя целиком передавать телефону ради одного кадра. Рекомендуется
серверное выделение кадров с pydicom; браузеру выдаются кадр и необходимые метаданные,
с сохранением signedness, bit depth, rescale, VOI и MONOCHROME1/2, а не заранее
контрастированный JPEG. Конкретный адаптер Cornerstone проверяется прототипом;
память и предзагрузка ограничены окном соседних кадров. Нельзя считать прохождение
синтетического несжатого файла доказательством поддержки реального Enhanced MR.

Альтернатива — Orthanc с DICOMweb: готовый медицинский протокол, но дополнительная
граница авторизации, индекс и восстановление. Пересмотреть выбор, если прототип
с реальными обезличенными CT/Enhanced MR не обеспечивает корректность и память.
Неподдерживаемая кодировка — явная ошибка просмотра и возможность скачать оригинал.
Набор кодеков (несжатые, JPEG, JPEG-LS, JPEG 2000, RLE) фиксируется только после тестов.

### Резервирование без закрытого ключа на сервере

Сохраняется модель age: на рабочем сервере только открытый ключ. Объекты неизменяемы,
поэтому каждый объект шифруется один раз для поколения ключа и переиспользуется в
последующих комплектах. Дамп и манифест шифруются отдельно для каждого комплекта.
Манифест связывает snapshot БД, ключи объектов, plaintext SHA-256 и ciphertext SHA-256.
Дедупликация между пользователями через доступное им API не вводится.

В 0.13.0 выбран простой протокол: общая блокировка изменений вложений и очистки →
экспорт PostgreSQL snapshot → pg_dump из snapshot и копирование неизменяемых объектов →
манифест и complete → снятие блокировки. Числовые записи продолжают работать;
изменения вложений временно отвечают 503. Это увеличивает окно недоступности загрузок,
зато не требует отдельного восстановления закреплений после сбоя процесса.

Каждый объект шифруется один раз на поколение ключа. plaintext SHA-256 проверяется до
шифрования, ciphertext SHA-256 — при повторном использовании и восстановлении.
Служебный references.json содержит только непрозрачные пути объектов. Автоматическое
удаление комплектов и разделяемых объектов в 0.13.0 не включено; политика хранения
требует отдельного решения. При настроенном BACKUP_REMOTE объекты переносятся перед
манифестами и маркерами complete; ошибка переноса завершает команду с ошибкой.

На пустом стенде владелец ключа расшифровывает комплект, проверяет оба hash, восстанавливает
объекты и соответствующую БД, затем включает приложение. Незавершённые upload/import
после восстановления явно сбрасываются или повторяются; старые multipart ID не возобновляются.
Срок хранения уже удалённых данных в резервных копиях равен сроку удержания комплектов.
Полная проверка согласованного восстановления БД и файлов — обязательный гейт реализации.

## Последствия и обязательные проверки

Новые контейнеры — хранилище и worker. Потребности сервера по диску/RAM вырастут;
существующий минимум установки для 0.12 нельзя переносить на DICOM без измерений.
Доступ к внутреннему хранилищу и обработка файлов потребуют изменения I11 и его гейта;
контракты файлов вводятся вместе с тестами, а не объявляются действующими заранее.

До завершения соответствующего шага 0.13:
- Превратить проверки условного копирования (старый ETag → 412, актуальный → успех)
  в интеграционный гейт полного протокола публикации с конкурирующим PUT.
- Проверить реальные обезличенные CT и Enhanced MR, все заявленные кодеки, память,
  сортировку, окно/уровень и браузеры iOS/Android; WebKit на Mac не заменяет телефон.
- Проверить Procrastinate/Python 3.14, перезапуск worker, отмену и повтор complete.
- Проверить согласованный snapshot БД/файлов, конкурирующее удаление, retention,
  потерю служебного индекса и восстановление на пустой установке.

Контрольные сценарии реализации: чужой файл/серия/кадр дают 404; неподписанная S3-операция
отклоняется; старый PUT не меняет опубликованный объект; повтор не создаёт дубля;
квота и ZIP-лимиты действуют на реальные данные; удалённый родитель не возвращается
после завершения worker; бинарники не попадают в офлайн-кэш; RU/EN и полный make check.

### Реализация 0.13.1 (готово, 2026-10-23)

Карточки исследований и вложения заключений используют общий механизм хранения.
Владение родителем теперь закреплено составными внешними ключами в базе.
Инспектор ZIP/CT/Enhanced MR реализован отдельно; он строит индекс метаданных,
а не подтверждает декодируемость пиксельных данных. Двухфазный импорт и очередь подключены; retry и восстановление по heartbeat проверяются
на PostgreSQL. Полные публичные архивы CT/Enhanced MR прошли загрузку, подтверждение
и импорт; восстановление после SIGKILL проверено на контейнере с частично записанными
объектами. Воспроизводимые проверки описаны в [TESTS](../TESTS.md). Покадровое декодирование и просмотр добавлены в 0.13.2; аппаратная проверка
iOS/Android остаётся условием закрытия версии.


### Реализация просмотра 0.13.2

Выбран отдельный экран с возвратом в карточку. Для STACK включены generic-адаптер и
CPU-путь 2D: он применяет линейный rescale к исходным целым пикселям и не требует
пула GPU-текстур. Кэш на телефоне сохраняет только текущий кадр, без prefetch;
следующий запрос начинается после предыдущего. Это экономит память ценой задержки
при листании. GPU и предзагрузка могут быть рассмотрены после измерений на устройствах.

Нативное скачивание ZIP использует короткую cookie, ограниченную оригиналом одного
исследования: браузер пишет большой архив потоком вместо накопления Blob в памяти.
Контракты — [I26](../INVARIANTS.md#i26-просмотр-не-меняет-смысл-пикселей-и-не-загружает-весь-объём),
границы ресурсов — [архитектура](../ARCHITECTURE.md), аппаратная проверка — [TESTS](../TESTS.md).
